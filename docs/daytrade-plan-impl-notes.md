## 2. 動かし方

```
node scripts/daytrade-plan.js                                # 自動（workflow_run 用）: 実行時刻の窓と済みの設計から、設計①②③／状態更新／何もしない、を決める
node scripts/daytrade-plan.js --resolve                      # 決めた種類を key=value で出すだけ（GITHUB_OUTPUT 用）
node scripts/daytrade-plan.js --run=design --slot=2          # 手動: 設計（枠 1=NY17:30 / 2=15:30 / 3=NY8:00）
node scripts/daytrade-plan.js --run=status                   # 手動: 状態更新（JST 16:00〜21:59 は型Bの追加も）
node scripts/daytrade-plan.js --run=design --slot=2 --dry-run --now=<ISO> --data-dir=<dir> --no-risk-feed   # 書き込まない試験
node scripts/daytrade-score.js
node scripts/daytrade-backtest.js [--window-days=365] [--no-fetch]
node --test scripts/daytrade/test/*.test.js
```

バックテストの結果（`data/daytrade/backtest-2026-10-09.csv`）は、コミット済みの H1 履歴と日足から再現できることを試験（`golden.test.js`）で固定している。バックテストの規則を意図して変えたときは、次で結果を作り直し、差分を確かめてからコミットする（H1 は再取得しない）：

```
node scripts/daytrade-backtest.js --no-fetch --now=2026-10-09T00:30:00+09:00
```

`.github/workflows/daytrade-tests.yml` が、`scripts/daytrade*` などを変える PR と main への push で、この試験と MTF の試験を動かす（外部へは接続しない・secrets は使わない）。

## 3. 既存のルールとの差（仕様 9-1 の「差分を列挙するだけでよい」）

| 項目 | 既存（`config/daytrade-rules.json` / `daytrade.js`） | 本仕様の生成器（統合せず別に計算） |
|---|---|---|
| High の窓 | 前15分〜後15分 | 前15分〜後30分 |
| Medium | 警告のみ（停止しない） | High と同じく停止（前15分〜後30分） |
| 指標・中銀の窓 | CPI・NFP 等は前後30分、中銀は前30分〜後60分 | 区別なし（High・Medium は一律） |
| 停止の対象 | 既存の通貨対応・ゲートの状態 | `pair_currencies` の2通貨に該当する High・Medium |
| 停止中の扱い | `gate.state` | 新規のみ禁止（案は残して『停止中』の印を付ける） |
| 鮮度 | `stale_min: 20` | 20分（同じ値。対象は intraday.json・daytrade-context.json・h1-bars.json の `as_of`） |

既存の `gate.state` は「参考：既存ゲート」として、生成時点のスナップショットを表示するだけ（停止判定には使わない）。

## 4. 仕様で迷った点（Q01〜Q57）

影響度：**blocking** = 結果の数字や出力の形が大きく変わるので、本人の回答を待ちたいもの / **material** = 数字が変わるが方向は変わらないもの / **minor** = 表示や細部。
どの項目も、候補を増やさない側・危険側に倒れない側の読みを暫定にしている（鮮度超過のときは発注不可、判断できないものは不採用／未取得／保留）。

## 5. 実データで分かったこと（バックテスト 2025-10-08〜2026-10-07）

- **SL幅10pips以上の門で、H1 ATR14 が小さい銘柄はA案がほとんど通らない。** A案（0.5×ATR）が10pips以上になるには H1 ATR14 が20pips以上必要。H1 ATR14 の中央値（pips）：EURUSD 9.9、GBPUSD 13.3、AUDUSD 8.7、USDCAD 10.0、USDCHF 8.9、EURGBP 5.9、USDJPY 17.5、EURJPY 18.0、XAUUSD 約170（1pip=0.1ドル）。そのため年間の案は型A（A案）で約110件、型B（A案）で6件ほどで、XAUUSD が型A・A案の約8割を占める。EURGBP は一度も出ない。仕様の数値の問題で、実装の都合ではない（本人の判断事項。パラメータは動かしていない）。
- **型Bは年間でごく少ない**（Q09：15:30の設計②では成立せず、設計③の21:00／22:00からしか出ない）。n が小さいので、型Bの行は読み取れない。
- **『pips合計』は銘柄を混ぜると XAUUSD が支配的**になる。銘柄の軸で見ること。
- H1履歴の時刻の解釈（`timezone=Asia/Tokyo`、`start_date`/`end_date` のページ送り）は、`h1-bars.json` の重なり500本との照合で確認した（取得時は全銘柄で不一致0、XAUUSD のみ取得値の桁（5桁）と `h1-bars.json` の桁（2桁）の差で2本。銘柄の桁に丸めて保存した現在の CSV では500本とも一致）。

## 6. 運用上の注意（実装の外）

- **入力の鮮度（Q14）**：`daytrade.yml` が intraday の完了直後に動くので、`intraday` が更新された直後は20分の基準を満たす。ただし `intraday.yml` の実際の更新は約2時間おきなので、更新が間引かれた時間帯は『発注不可（鮮度超過）』になる。`intraday.yml` の更新頻度の改善は別件（このPRでは触らない）。
- **起動（Q22）**：`daytrade.yml` は cron を使わず、`Intraday Snapshot` の完了（workflow_run）で動く（GitHub の `schedule` の欠落・遅延の影響を受けない）。`Intraday Snapshot` が動かなければ `daytrade.yml` も動かない（`intraday.yml` 側の cron の欠落は別件）。待機中の run が置き換わっても、設計は『その枠で最初の実行』で決まるので抜けない。手動は `workflow_dispatch`（`run=auto|status|design`＋`slot`）。
- **カレンダー（Q23）**：`economic-calendar.json` は当日（JST）分だけ。0:00〜3:00のイベントは、日付が変わった後に `intraday` が更新されてから拾われる。
- **口座の更新**：`data/daytrade/accounts.json` の `equity_jpy` は本人が手で更新する（README に書いてある）。
